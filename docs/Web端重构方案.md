# WeChatSend Web 端重构方案

> 版本：2026-09-12 · 范围：`web/frontend` 与 `web/backend` · 不修改微信小程序

## 1. 重构目标

本轮不新增业务范围，重点解决页面结构、交互规则、代码边界和维护成本问题：

1. 用户可以按“配置发送能力 → 管理客户 → 准备内容 → 创建任务 → 查看结果”的自然顺序完成工作。
2. Web 保持黑白极简，绿色和红色只表达成功、失败等语义状态，不再承担品牌装饰。
3. 页面只负责组织视图；复杂状态和业务步骤下沉到 feature hook 或业务组件。
4. API、格式化、导航、加载、错误、表单和弹窗使用统一实现。
5. 后端按业务域组织 Nest 模块，数据库连接池和认证基础设施只有一个实例。

## 2. 产品信息架构

| 一级区域 | 页面 | 用户目标 |
| --- | --- | --- |
| 运营 | 工作台、发送任务、创建任务、任务详情 | 创建、执行、追踪一次发送 |
| 客户 | 发送账号、好友管理 | 建立 iPhone/邮箱通道，维护唯一好友备注、分组和标签 |
| 内容 | 文案模板、内容变量、AI 助手 | 准备可复用且可预览的消息内容 |
| 账户 | 会员套餐、订单记录、个人中心 | 管理权益、交易和登录身份 |
| 管理 | 平台配置、支付与套餐、内容库审核、全部订单 | 管理平台能力和运营资产 |

导航不再把所有页面平铺。管理员入口与普通业务入口分离，页面标题由统一路由表生成。

## 3. 核心用户流程

### 3.1 首次使用

1. 登录后进入工作台。
2. 添加发送账号并验证接收邮箱。
3. 添加好友，确保同一账号下微信备注唯一。
4. 创建任务，依次完成内容、对象、时间和确认四步。
5. 在任务详情查看邮件投递和微信反馈两个独立状态。

### 3.2 日常发送

1. 从模板、AI 草稿或历史任务复制进入任务创建器。
2. 选择一个或多个发送账号，再按好友、分组或标签选择对象。
3. 立即发送默认使用当前时间；定时发送必须晚于当前时间。
4. 每个账号只使用已启用且邮箱已验证的配置，间隔不得低于 10 秒。
5. 提交前生成稳定预览，提交后内容和变量版本冻结。

### 3.3 结果处置

1. 邮件状态和微信反馈状态分栏显示，避免把“SMTP 已接受”误认为“微信已发送”。
2. 微信反馈超过一分钟显示超时，并提示核对好友备注。
3. 仅失败或未知的邮件允许人工重发，操作前使用产品内确认弹窗提示重复风险。
4. 任务取消只影响尚未投递的邮件。

## 4. 前端结构

```text
web/frontend/src
├── components
│   ├── ui/                 # Button、Card、Input 等基础组件
│   ├── app-shell.tsx       # 响应式应用框架和分组导航
│   ├── dialog.tsx          # 统一弹窗
│   ├── form-field.tsx      # 统一标签、必填和帮助信息
│   ├── page.tsx            # 页面标题、区块标题、指标和定义项
│   ├── toast.tsx           # 全局成功、失败和信息提示
│   └── states.tsx          # 加载、错误、空状态
├── features
│   ├── task-builder/       # 四步任务创建器、状态 hook、数据类型
│   └── admin-console/      # 管理后台各配置面板和类型
├── hooks
│   └── use-resource.ts     # 防止旧请求覆盖新请求的统一加载模型
├── lib
│   ├── api.ts              # Token、401、请求和错误边界
│   ├── format.ts           # 日期、金额等展示格式
│   └── navigation.ts       # 唯一导航和路由标题来源
└── pages                   # 页面级编排，不承载可复用复杂流程
```

页面通过 `React.lazy` 按路由拆包。`useResource` 统一加载、重试和竞态保护；写操作仍由页面或 feature hook 明确触发，不把隐式副作用藏进展示组件。

任务列表使用 `GET /api/v1/tasks/page?page=1&pageSize=20&search=` 做服务端分页和搜索。原 `GET /api/v1/tasks` 保留，避免影响小程序和已有调用。

## 5. 后端模块边界

```text
AppModule
├── CoreModule             # Prisma、认证守卫、邮件、微信 access token
├── IdentityModule         # 账号密码、邮箱、微信、小程序身份
├── MessagingModule        # 账号、好友、分组、模板、变量、草稿、任务、反馈
├── IntelligenceModule     # AI、外部 API、导入、平台配置
├── BillingModule          # 支付宝、微信支付、虚拟支付、订单、权益
└── SystemModule           # 健康检查
```

`CoreModule` 是唯一全局基础设施模块，避免 feature 模块重复创建 Prisma Client 或连接池。业务模块通过显式 `imports/exports` 建立依赖；例如任务模块只通过 `IntelligenceModule` 使用外部变量解析服务。

任务域已将 HTTP 参数、认证上下文和路由装饰器留在 `tasks.controller.ts`，数据库事务、配额和任务规则下沉到 `TasksService`。后续业务规则不应重新写入 Controller。

## 6. 视觉与交互规范

- 画布：暖灰白 `#f6f6f3`，卡片白色，正文近黑色。
- 主操作：黑底白字；次操作：白底黑边；危险操作：红色。
- 成功、失败颜色仅用于状态、验证结果和风险提示。
- 页面统一由 eyebrow、主标题、说明和右侧操作组成，标题下有清晰分隔线。
- 卡片圆角统一为 16px，表单控件圆角约 10px，焦点统一为黑色描边。
- 不使用浏览器原生 `prompt` 或 `confirm`；所有编辑、确认和危险操作使用应用内弹窗。
- 加载、空数据和失败必须有独立状态；错误区域使用 `role="alert"`，成功提示使用 `role="status"`。
- 动画只用于轻量页面进入，并尊重 `prefers-reduced-motion`。

## 7. 本轮已完成

- 重做应用框架、分组导航、响应式侧栏和统一页面标题。
- 全路由懒加载，降低初始脚本体积。
- 重做工作台、任务列表、四步任务创建器、任务详情、登录、个人中心、会员、订单、账号、好友、模板、变量和 AI 页面。
- 任务创建器从页面拆为状态 hook、步骤组件和类型文件。
- 管理后台拆为独立业务面板，模型新增与测试改为结构化弹窗。
- 好友分组/标签和变量表格导入改为结构化弹窗，移除原生输入框。
- 统一 API 的 Token 和 401 处理，统一日期、金额、加载、错误和空状态。
- 后端从单一巨型 `AppModule` 拆为五个业务模块和一个核心模块。

### 7.1 第二轮工程优化

- 任务 Controller 与业务 Service 分离，控制器仅做认证用户和请求参数转交。
- 新增任务服务端分页与标题/内容搜索，同时保持旧接口兼容。
- 新增全局 Toast，替换平台配置、身份绑定和支付后台的临时成功文案。
- 新增 Playwright 浏览器测试基础，覆盖桌面/移动端登录入口和任务列表分页搜索。
- 新增任务分页与租户隔离单元测试。

## 8. 后续维护规则

1. 新页面必须使用 `Page` 与 `PageHeader`，不再复制标题 DOM。
2. 新弹窗必须使用 `Dialog`，危险操作必须明确说明影响范围。
3. 同一业务流程超过一个页面或约 100 行状态逻辑时，放入 `features/<domain>`。
4. 请求错误必须显示服务端可行动提示；禁止只记录到控制台。
5. 颜色、日期、金额、状态名称和导航不允许在多个页面各自定义。
6. 每次提交至少执行 `npm run typecheck`、`npm run test` 和 `npm run build`；涉及关键页面流程时执行 `npm run test:e2e -w @wechatsend/frontend`。首次运行需先执行 `npx playwright install chromium`。
7. 小程序后续对齐功能时复用接口契约和文案语义，不照搬 Web DOM 或布局。

## 9. 建议的下一轮工程债务

本轮保持 API 契约和数据库结构不变。后续建议按优先级继续：

1. 在已有 Playwright 基础上补任务创建、身份绑定、支付下单的沙箱流程测试。
2. 继续拆分 `TasksService` 中的对象解析、配额预占和内容冻结规则，并为其他复杂 Controller 建立领域 Service。
3. 为好友、模板和变量等其余大列表增加服务端分页。
4. 将写操作错误逐步接入统一 Toast，并保留表单字段级错误和可重试页面错误。
5. 接入可观测性，分别记录 API 延迟、队列等待、SMTP 投递和反馈超时。
